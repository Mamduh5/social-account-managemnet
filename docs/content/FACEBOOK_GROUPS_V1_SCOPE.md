## Supported possibilities and limitations

| Situation | Useful path | Evidence required before an action |
| --- | --- | --- |
| Owner-administered/moderated Group | Prepare a Group-specific draft; owner may use Facebook's native schedule if the control is available for the exact identity/role. | Exact Group URL, actual admin/moderator role, acting Page/profile, rules and visible native scheduling capability. Native scheduling must retain its own saved evidence; an SCC reminder is not a Facebook schedule. |
| External Group, member only | Prepare a relevant manual handoff/reminder. Submit only with separate exact owner approval and current posting permission. Admin approval may be required. | Current membership/participation status, permitted identity, topic/promotional/link/media rules, moderation and restrictions. Never assume member scheduling. |
| Page may participate | Use the exact joined Page shown in the composer. A Page Graph token establishes no Group membership or posting permission. | Visible acting Page and Group context, independent of the Page's SCC API connection. |
| Group allows profiles only | Retain an owner-only profile handoff if specifically selected; current native action ledger deliberately requires a Page. | Explicit profile identity/authority; do not silently switch from a rejected Page or expand the Page-only executor. |
| Share an existing published Page post | Prefer its existing permalink and a short relevant introduction **when the native Share-to-Group control and rules permit it**. | Exact Page original, allowed links/self-promotion, actual identity, accessible share control and resulting Group receipt. Sharing is a separate publication, not covered by the Page receipt. |
| New Group-specific post | Prepare an original discussion/technique explanation with linked source/media provenance. | Group relevance and exact content/media approval. New uploads need separate permission; don't imply a Page asset was shared merely because it was copied. |

Meta removed the public Groups API, including `publish_to_groups` and `groups_access_member_info`, across API versions on **22 April 2024**. There is no supported SCC Page Graph-to-Group publishing path. Meta's [v19 announcement](https://developers.facebook.com/blog/post/2024/01/23/introducing-facebook-graph-and-marketing-api-v19/) and [v19 changelog](https://developers.facebook.com/docs/graph-api/changelog/version19.0/) are the primary references; both returned HTTP 429 in this fresh research pass, so their contents were not independently re-read here. No replacement API or permission is claimed.

Meta documents native Group scheduling for admins/moderators in its [official Communities Summit announcement](https://about.fb.com/news/2017/06/our-first-communities-summit-and-new-tools-for-group-admins/). The [current Help Center scheduling reference](https://www.facebook.com/help/124331564818285) redirected to a login/block page during this assessment. ## Recommended smallest V1

Reuse **Groups Workspace** and its existing manual handoff/native-intent ledger. Start only with the owner-selected registered external AI short-film Group, acting as World where current Facebook permissions allow, one reviewed item at a time. Owner selection of the Group is not approval of a specific post. No new Groups scheduler, API connector or bulk-posting engine is needed.

1. Refresh a per-Group evidence card: Group URL, owner admin/member role, allowed Page/profile, membership and participation approval, rule text/date, links/self-promotion/media restrictions, moderation, current account restrictions, and whether the exact native composer supports scheduling.
2. Choose a share of an existing Page receipt or a Group-specific draft. Save the exact Group/identity/rules revision, relevance, content/media provenance and proposed time in the existing handoff; preserve its original snapshot on later rule changes.
3. Obtain separate owner approval for that exact Group action. The initial V1 uses owner-completed manual posting/scheduling. A later specifically authorized browser-assisted action is limited to the visible native UI, one exact intent, supported controls and current permissions. Never use private GraphQL/undocumented endpoints or reinterpret a Page token as Group access.
4. Record `submission_started` before one remote submission through the existing native-intent workflow. Preserve `pending_approval`, `restricted`, `uncertain` and `published` distinctly; reconcile an interrupted original without resubmitting. Save a Group permalink/observed result. Owner-entered/browser observations retain their actual provenance and do not become official API verification.
5. Use manual reminders for member Groups. Record native schedules only after the exact Facebook UI confirms them. An opened package, copied caption, Page publication, SCC reminder or approved membership proves no Group publication.

Posting repeated links/captions across many Groups, excessive frequency, ignored promotional rules and retrying through restrictions can lead to spam/account restrictions. No universal “safe daily count” is established. V1 deliberately requires relevance, a per-item owner choice and a stop on Facebook restrictions/security prompts; it does not rotate identities or attempt to evade limits. Related Page work remains governed by its own actual account/grant restrictions, rather than a blanket Groups-triggered pause.

Existing implementation: `server/src/services/groups-workspace.service.ts` (registry/review, snapshots, reminders, receipt history), `groups-native-actions.service.ts` (exact-Page intent, duplicates, submission/reconciliation), corresponding repositories/routes, and `client/src/components/groups/GroupNativeActions.tsx`. Eighteen isolated native-action tests passed in this assessment; that is local control validation, not fresh Facebook UI or live Group-post acceptance.
